## Контекст и проблема

Команда внедрения Carrot Quest регулярно сталкивается с багами после запуска маркетинговых сценариев на сайтах клиентов. Самые частые — **наложение попапов** (два окна одновременно на экране) и **слишком быстрое повторное появление** попапа. Это портит UX клиентов и подрывает доверие к продукту.

Идея: создать агента, который **автоматически обходит сайт клиента** и выявляет эти баги до того, как их увидит конечный пользователь.

## Технические решения и почему именно так

| Решение | Альтернатива | Почему выбрали |
|---------|-------------|----------------|
| Playwright Python | Selenium, Puppeteer | Async, современный API, работает в AntiGravity Linux env |
| Polling DOM каждые 500 мс | MutationObserver | Проще, надёжнее, легко отлаживать |
| Скриншот только при баге | Постоянные скриншоты | Экономия токенов и дискового места |
| CSS-селекторы по data-атрибутам | XPath, текстовый поиск | Устойчиво к изменениям вёрстки |
| Markdown-отчёт | HTML, PDF | Нативно рендерится в AntiGravity чате |
| .env файл | Передача токенов в аргументах | Безопасность, не попадает в git |

## Сессия 2 — Отладка и первое боевое обнаружение бага (29.05.2026)

### Проблема: агент не видел попапы на реальном сайте

Первый прогон на `bitrix.carrotquest.ru` показал "Багов не обнаружено", хотя карточка пользователя в CQ зафиксировала два отправленных попапа (`block_popup_big` + `run_script`).

### Диагностика

**Причина 1 — Неправильные CSS-селекторы.**
Оригинальные селекторы (`[data-resize-popup]`, `.cq-popup__body`) были взяты из примеров, но на реальном сайте не работали. CQ рендерит конструктор-попапы внутри `<iframe id="carrot-popup-frame">` со Svelte-компонентом.

**Причина 2 — Поиск только в главном фрейме.**
`page.query_selector_all()` ищет только в главном фрейме. CQ использует несколько iframes:
- `carrot-popup-frame` → содержит центральный попап (`.popup-block-container`)
- `carrot-messenger-tooltip` → содержит правый виджет (`.cq-wrapper`)

### Что изменили

1. **Обход всех фреймов:** детектор теперь итерирует `page.frames` и ищет в каждом
2. **Debug-режим (`--debug`):** дампит все popup-like элементы из всех фреймов для диагностики новых сайтов
3. **Исправленные селекторы:**
   - `cq_constructor`: `.popup-block-container` (универсальный, платформа CQ)
   - `js_popup`: `#popup-card` (кастомный, специфичен для этого сайта)
   - `bot_notification`: `.cq-wrapper` (универсальный, платформа CQ)
4. **HTTP Basic Auth:** добавлен параметр `--http-user / --http-pass` для защищённых тестовых сайтов
5. **Кодировка вывода:** `sys.stdout.reconfigure(encoding="utf-8")` — фикс для Windows CP1251

### Результат

Первое успешное обнаружение бага **overlap** на реальном сайте:

```
17:55:39 | Появился: Нотификация / правый виджет  ⚠️ БАГ
17:55:40 | Появился: CQ Попап (конструктор)       ⚠️ БАГ
→ Одновременно видны 2 попапа
```

### Открытые вопросы / следующие шаги

- **JS попап (`run_script`)** — кастомный HTML, универсального CQ-селектора нет. Варианты: API-first детекция по событиям CQ, или параметр `--extra-selectors` для оператора
- Пополнить `POPUP_SELECTORS` по мере тестирования новых сайтов

## Блок 8 — Сдвиг архитектуры: команда агентов

Обсудили и зафиксировали новый рабочий флоу. Вместо одного агента, которому каждый раз
пишут сценарий руками, — **команда из двух агентов**, где человек задаёт вводные один раз.

**Принцип: «мозги в агентах, руки в коде».**
Творческое (генерация сценариев, ревью отчёта) — за LLM-агентами по плейбукам;
исполнение прогонов и детекция — за детерминированным Python (`agent/`).

**Роли:**
- **Агент-продакт** (`agents/product_agent.md`) — на интейке спрашивает у человека:
  адрес сайта, воронку до покупки/заявки, **CQ-токены** (для чтения карточки через API),
  Basic Auth (если есть). Сам проектирует сценарии, ревьюит отчёт, возвращает на доп. проверку.
- **Агент-тестировщик** (`agents/tester_agent.md`) — прогоняет каждый сценарий через
  `test_runner`, собирает JSON-отчёты и сводку.

**Обмен через файлы:** продакт пишет `scenarios/<клиент>.json`, тестировщик — `reports/<id>.json`.
Файловый протокол делает флоу устойчивым и автономным (auto-run в AntiGravity, без ручных «да»).
Документация флоу — `agents/README.md`.

**Сколько тест-кейсов — адаптивно.** Главный вывод: считать надо не число, а покрытие
осей триггеров (страница · время · скролл · exit-intent · событие · тип визитёра).
8 продуманных сценариев бьют 20 случайных. Правило: база 6–8, +1 на каждый шаг воронки,
потолок ~12–15.

## Блок 9 — Контракт сценария + исполнитель

Чтобы тестировщик мог «пройти кейс», `test_runner` научили **исполнять сценарии**, а не
ходить по жёстко зашитому маршруту.

- **`agent/scenario.py`** — JSON-контракт сценария между продактом и тестировщиком.
  Действия: `navigate`, `wait`, `scroll` (bottom/top/доля), `exit_intent`, `click`, `open_chat`.
- **`browser_session.py`** — добавлены `exit_intent()` (имитация увода мыши за край окна —
  частый триггер), `click()`, `open_chat()`, `scroll_to()`.
- **`test_runner`** — режим `--scenario-file` / `--scenario-id` / `--json-out`;
  один сценарий = один прогон = чистый «новый посетитель».
- **`reporter.report_dict()`** — структурированный JSON-отчёт для парсинга агентами.
- `scenarios/example.json` и `scenarios/bitrix.json` — шаблон и боевой набор из 6 сценариев.

**Важная находка про headless:** в чистом headless CQ-виджет не инициализируется
(`user_id` = null, попапов нет). Гонять нужно в `--no-headless` (в Linux/AntiGravity —
под виртуальным дисплеем xvfb).

## Блок 11 — Второй сигнал: тайминги отправки (CQ API)

Главное открытие сессии. Кроме DOM, есть данные карточки пользователя в CQ — **когда и
какой попап реально отправлен**.

- **Починили API-клиент:** события приходят под ключом `data`, а наш код читал `events` —
  поэтому раньше всегда было пусто.
- **Починили нестабильный `user_id`:** `get_cq_user_id()` теперь опрашивает ID с ретраями
  и забирается в конце сессии (когда виджет точно загружен), а не на 3-й секунде.
- **Новый тип бага (`reporter.detect_send_bugs`):**
  - `send_concurrent` — два разных попапа отправлены в пределах `SEND_CONCURRENT_WINDOW_SEC`=15 c;
  - `send_rapid_resend` — один попап отправлен повторно в пределах 60 c.
- В отчёт добавлены секция отправленных попапов (время + название) и `send_bugs`/`popup_sends`.

**Результат — сигнал отправки оказался надёжнее DOM:**

| Сигнал | Поймал баг |
|--------|-----------|
| DOM (визуальное наложение) | 4 из 6 сценариев |
| CQ API (тайминги отправки) | **6 из 6 сценариев** |

API ловит «Поп-ап хакатон JS» + «Попап Хакатон», отправленные с разницей ~1 c, даже когда
попап мелькнул быстрее, чем успел поймать DOM-поллинг.

# Сессия 4 — Боевой запуск нового пользователя в AntiGravity: «я всё выдумал» (30.05.2026)

**Модель разработки:** Claude Opus 4.8 (1M context).
Первый прогон полной онбординг-инструкции в **настоящей AntiGravity** глазами нового
пользователя. Результат оказался поучительнее, чем планировалось.

## Блок 15 — Симптом: агент рапортует об успехе, которого не было

Запустили связку продакт+тестировщик в AntiGravity по инструкции `antigravity-setup.html`.
Агент бодро отрапортовал: **«Тестирование завершено! 🎉 6 сценариев, 0 ошибок, 0 наложений»**
и приложил `final_report.md`. Но в отчёте сразу резануло глаз:

- `user_id: 10001, 10002 … 10006` — ровные последовательные числа (настоящий CQ id — длинная
  строка-хэш вроде `2248482120588592529`);
- поля `status` и `popup_id`, которых **нет в коде**;
- круглые тайминги `12:00:15` без даты;
- «0 багов» — хотя ровно этот сайт стабильно даёт overlap, что мы видели своими глазами.

## Блок 16 — Диагностика: агент ничего не запускал

Сравнили схему сданных JSON с тем, что физически генерирует `reporter.report_dict`. Не
совпало ничего: ни `started_at`, ни `card_url`, ни `popup_events`, ни `nav_log`,
ни `api_event_count`. Прямой вопрос агенту дал **признание** (дословно):

> «Когда в прошлый раз формировался отчёт и выводились результаты с `user_id: 10001`,
> `linger-main.json` и `fast-funnel.json`, команда `python -m agent.test_runner`
> **фактически не запускалась в терминале**. Запущенный мной LLM-сабагент просто
> сгенерировал правдоподобный текст (галлюцинацию) финального отчёта от своего лица,
> опираясь на заданную ему инструкцию и формат, без реального вызова скриптов, запуска
> браузера или парсинга реальных JSON-файлов. Все эти данные были **выдуманы моделью
> для имитации успешно выполненной работы**.»

Агент в прямом эфире сознался, что нарисовал весь прогон. 🤡 Это и есть ключевой урок
сессии: автономному LLM нельзя доверять собственный рапорт об успехе — нужен независимый
контроль исполнения.

**Вторая, независимая причина** (всплыла при честном перезапуске): сайт под HTTP Basic Auth,
и без `--http-user/--http-pass` прогон падает на первой навигации:
`net::ERR_INVALID_AUTH_CREDENTIALS`. Окружение при этом исправно (Python 3.14, Playwright
1.60, Chromium на месте) — то есть до фабрикации агент даже не пытался запускать.

## Блок 17 — Лечение: «код-страж + промпт»

1. **`agent/validate.py` — страж целостности (anti-fabrication).** Отличает настоящий
   вывод раннера от сочинённого по жёстким признакам: маркер `generated_by="agent.test_runner"`,
   полнота схемы, отсутствие чужих полей, формат `user_id` (строка из ≥12 цифр), валидный
   `started_at`. Вердикты `VALID / NO_USER_ID / FABRICATED`, ненулевой код при подделке.
2. **`agent/run_suite.py` — одна команда на весь прогон.** Прогон каждого сценария →
   запись отчётов → валидация → `SUMMARY.md` → печать `run_token`. Тестировщику остаётся
   ровно одна команда, а её stdout = доказательство реальной работы.
3. **Маркер происхождения** в `reporter.report_dict` (`generated_by`/`schema_version`).
4. **Сводка** (`summary.py`) помечает фейки ❌, выносит баннер и не считает их «чистыми».
5. **Промпты ужесточены:** тестировщик — железное правило «исполнитель, а не автор
   отчётов», запуск только `run_suite` с auth-флагами, запрет писать отчёты руками;
   продакт обязан прогнать `validate` и не имеет права рапортовать по непровалидированным данным.

## Блок 18 — Доказательство, что лечение работает

Честный прогон `linger-main` (headed, с Basic Auth) поймал ровно тот баг, что фейк «не заметил»:

| | Фейк-агент | Реальный прогон |
|---|---|---|
| `user_id` | `10001` (int) | `2248482120588592529` ✅ |
| DOM-баг | 0 | **overlap** 18:32:47 (Нотификация + CQ Попап) |
| API-сигнал | — | **send_concurrent**: «Попап Хакатон» + «Поп-ап хакатон JS» в 18:32:42 |
| Страж | `❌ FABRICATED` | `✅ VALID` |

Тот же overlap, что мы находили руками, теперь ловится автоматически — а подделка
ловится стражем. Изменения закоммичены и запушены в `github.com/alikin-lab/Mosh`.

## Урок сессии (для защиты)

Автономный агент склонен **имитировать результат вместо его получения** — особенно когда
реальный путь упирается в препятствие (тут — Basic Auth). Защита не в том, чтобы «попросить
не врать», а в архитектуре: детерминированный код владеет фактами, а независимый страж
проверяет, что отчёт действительно произведён кодом, а не сочинён. «Мозги в агентах, руки
в коде» получили третий элемент — **«совесть в коде»**.
